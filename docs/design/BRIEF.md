## 1. Что уже есть и считается эталоном

- **Переключатель дизайна.** `useThemeStore().design` = `'classic' | 'modern'`; на `<html>` стоят
  `data-design` и `data-theme` (`theme/applyDocumentTheme.ts`). Новый дизайн включается в панели
  аватара («Новый дизайн (бета)»). Классика будет удалена позже, отдельным решением пользователя.
- **Стекло.** `frontend/src/theme/glass.css` — матовое стекло в духе visionOS. Переменные:
  `--win-*` (большое окно), `--panel-*` (панели внутри окна), `--chip-*` (пилюли периода),
  `--field-bg`, `--table-solid`, `--menu-active-bg`, `--glass-text`, `--hdr-btn`, `--hdr-rim`.
  Все правила привязаны к `html[data-design='modern']:has(.app-shell)`.
- **Токены antd.** `frontend/src/theme/tokens.ts` → `antThemeConfig('modern', mode)`: primary
  `#2563eb` / `#4f8cff`, Inter, radius 8/12, `colorBgContainer` полупрозрачный (поэтому инлайновые
  фоны «контейнера» на страницах уже стали стеклом), `colorBgElevated` сплошной для модалок.
- **Готово в новом дизайне** (не переделывать, брать как образец):
  - каркас `components/Layout.tsx`: плавающее меню (`sider-*`, hover-glider, раскрытие при
    наведении), шапка `components/ModernHeaderBar.tsx` (`hdr-*`, панель профиля), нижняя панель
    `components/BottomTabBar.tsx`; окно стоит на месте, прокручивается содержимое;
  - на дашборде — только приветствие и пилюля периода (`components/DashboardGreeting.tsx`, `dash-*`).
    Всё ниже приветствия — классический JSX, перекрашенный глобальным CSS, и это **не эталон**:
    разбор и ТЗ на пересборку — `DASHBOARD.md`;
  - общие правила для всех страниц (конец `glass.css`): `h4.ant-typography` → 28px, обычные кнопки
    стеклянные, теги-пилюли, модалки/дроверы/поповеры/селекты/пикеры — стекло, тёмная палитра тегов.
- **Карта страниц и прав** — `frontend/src/config/modernMenuTree.ts` (разделы → пункты → роли).
- **Мобильный порог** 768px: `hooks/useIsMobile.ts`, `mobile.css`, `components/MobileCardList.tsx`,
  семантические классы `APP_BUTTON` / `APP_INPUT` (`components/ui/AppClassNames.ts`).
  Скрипт `scripts/check-mobile-breakpoint.mjs` проверяет согласованность порога при сборке.
- **Хелперы форматирования**, которые надо переиспользовать, а не дублировать: `utils/currency.ts`,
  `utils/phone.ts`, `lib/name-utils.ts`, `dayjs`; статусы сделок — `components/DealStatusTag.tsx`;
  скролл-фейд таблиц — `hooks/useTableScrollFade.ts`; подсветка за курсором — `hooks/useHoverGlider.ts`.
- **Иконки.** В новом дизайне — `@phosphor-icons/react` (меню, шапка, нижняя панель).
  `@ant-design/icons` остаётся в старом коде страниц.

## 3. Принципы — что значит «хорошо»

1. **Один вопрос на страницу.** У каждой страницы есть вопрос, на который она отвечает
   (Клиенты: «кому звонить и кто должен»; Сделки: «что застряло и где деньги»; Остатки: «что
   кончается»). Всё, что видно по умолчанию, служит этому вопросу; остальное — на клик.
2. **Иерархия:** заголовок 28px → KPI → управление (поиск, фильтры, пилюли) → данные.
   Один визуальный акцент на экран.
3. **Цвет — только смысл:** статус, дельта, риск, активный элемент. Остальное нейтрально.
   Никаких декоративных градиентов, кроме уже принятых goal-bars на дашборде.
4. **Плотность:** таблица по умолчанию ≤ 7 колонок на десктопе; числа вправо и
   `font-variant-numeric: tabular-nums`; длинное — обрезка + тултип; детали — в дровере/раскрытии.
5. **Сетка 4px.** Радиусы: окно 40, плавающие панели 20, группа внутри окна (`Section`) 16,
   строки/кнопки/поля 10, пилюли 999; значения 24 в словаре нет. Тени — только у плавающих
   слоёв (меню, дроверы, поповеры); у панелей внутри окна — rim (`--panel-rim`), не тень.
6. **Оба режима и обе ширины обязательны:** светлая/тёмная тема, ≥1280 и 390px. Контраст текста на
   стекле ≥ 4.5:1 — проверять на тёмной теме с фоном-фотографией.
7. **Движение** 150–200ms, `prefers-reduced-motion` уважать (как в `glass.css`). Hover-glider —
   только в меню и панелях, не в таблицах.
8. **Иконки** в новых компонентах — Phosphor 18/20px, `regular`, `fill` для активного.
   Не смешивать с `@ant-design/icons` внутри одного нового компонента.
9. **Пустое значение — «—»**, не пустая ячейка, не `null`, не `undefined`. На экране не бывает сырых
   ISO-дат, UUID, внутренних enum-ключей (`WAITING_FINANCE`) без подписи.
10. **Классика не ломается** (нет ошибок, разметка цела), но улучшать её не нужно.
11. **Рабочие страницы с телефона** (подтверждение склада, мои отгрузки, маршрут, моя машина,
    посещаемость) — приоритет крупные цели касания (≥44px), читаемость на солнце, минимум шагов;
    стекло там допустимо приглушить до почти сплошных панелей.

## 4. Данные: лишнее / добавить / нормализовать

### 4.1 Аудит перед правкой каждой страницы

Для каждого отображаемого поля (колонки, пункта `Descriptions`, `Statistic`, тега) — класс:

- **P (primary)** — нужно, чтобы на этой странице принять решение или совершить действие → остаётся
  в основном виде.
- **S (secondary)** — полезно иногда → уходит на клик: дровер/раскрытие строки, тултип,
  «Показать ещё», настройка видимых колонок, вкладка «Подробнее».
- **N (noise)** — дублирует другое поле; внутренний id; техническая метка времени, бессмысленная
  для этой роли; почти всегда пусто; производное, которое и так видно → убрать из вида.

Аудит показывается в ответе сессии таблицей «поле · класс · куда уходит / что добавлено»,
а в `PROGRESS.md` остаётся одна строка решений по странице.

### 4.2 Правила удаления

- «Убрать» = **скрыть из вида по умолчанию**. Не удалять поля из типов и API, не удалять действия
  и доступы. Действия можно сворачивать в меню «⋯» или в дровер.
- **Проверять роли.** Страницу видят роли из `modernMenuTree.ts` и гейтов в коде страницы. Поле,
  нужное хотя бы одной роли для её работы, остаётся для этой роли (условный рендер).
- **Сомнение → не убирать**, записать в `QUESTIONS.md` (формат в §9) и идти дальше.
- Не трогать смысл бизнес-текстов и ключи `localStorage` / URL-параметров.

### 4.3 Что добавлять

Только то, что уже приходит с API или лежит в типах (`src/types/index.ts`, `src/api/*.api.ts`):

- признаки, отвечающие на вопрос страницы: долг и просрочка, дни в текущем статусе,
  «последний контакт N дн. назад», сумма последней сделки, ответственный, SVIP/риск-метки;
- счётчики в подписях вкладок и фильтров («Долги · 12»), дельта к прошлому периоду у KPI;
- «кто и когда» у изменяемых сущностей — в деталях, не в таблице.

Данных нет в API → в раздел BACKLOG файла `QUESTIONS.md` с сущностью и полем. Бэкенд в рамках
редизайна **не трогаем**. Единственное исключение: аддитивно вернуть в ответ списка поле,
которое уже есть в Prisma-модели, ≤ 20 строк, без миграций, с упоминанием в теле коммита.

### 4.4 Нормализация — единые правила

Выносить в хелперы и примитивы, не копировать по страницам:

- **Деньги:** пробел-разделитель тысяч, без копеек если нули, валюта после числа, отрицательные —
  со знаком и цветом риска; один хелпер в `utils/currency.ts` и примитив `Money`. `Money` обязан уважать скрытие сумм
  (`isMoneyHidden`, `HIDDEN_MONEY`, `MoneyAccessGuard`): роли без доступа к деньгам видят `•••`, как сейчас.
  На дашборде — исключение по таблице доступа к деньгам в `DASHBOARD.md` §6 (денежная плитка не рендерится).
- **Даты:** `DD.MM.YYYY`, время `HH:mm` только когда важно; «сегодня / вчера / N дн. назад» для
  недавних событий с полной датой в `title`; никаких разнобойных `toLocaleString`.
- **Телефоны** — `utils/phone.ts`; **имена** — `lib/name-utils.ts` (короткое имя в таблицах,
  полное в карточке).
- **Статусы:** одна карта «статус → цвет, подпись» на сущность, один компонент `StatusPill`;
  одинаковый цвет статуса на всех страницах (сделки — через `DealStatusTag`).
- **Порядок колонок:** идентичность → статус → деньги → люди → время → действия.
  Действия — последняя колонка, иконки с `aria-label`.
- **Единицы** всегда рядом с числом (кг, шт, %). **Проценты** — одна цифра после запятой.
- **Адреса, заметки, реквизиты** — в деталях, не в таблицах.

## 5. Слой примитивов `frontend/src/components/ui/`

Шесть примитивов языка (`Section`, `Eyebrow`, `StatTile/StatGrid`, `Money`, `EmptyState`, `StatusPill`)
рождаются на дашборде (`DASHBOARD.md` §8, шаг 3), остальные — на пилоте Клиентов. Затем используются на всех
страницах. У каждого — `.tsx` и `.css` рядом,
BEM-классы с префиксом `ui-`, базовые стили нейтральны (работают и в классике), стеклянные —
под `html[data-design='modern']`. Без инлайновых стилей; цвета только из CSS-переменных и
antd-токенов (`var(--ant-color-text)` и т. п.).

| Примитив | Назначение | Что заменяет |
|---|---|---|
| `PageHeader` | `title`, `eyebrow`/`subtitle`, `meta` (счётчик, статус), `actions` справа, `back`; на мобиле actions уходят вниз или в «⋯» | ручные `Title level={4}` + `BackButton` + `Space` |
| `Toolbar` | поиск + фильтры + сегментированные пилюли + «Сбросить»; на мобиле — одна строка + кнопка «Фильтры» (дровер); не ломает `useUrlSearchDraft` | произвольные `Space wrap` и `Row/Col` с фильтрами |
| `StatTile`, `StatGrid` | число + подпись + дельта, как `dashboard-metric-card` | разрозненные `Statistic` и `Card` с цифрой |
| `DataTable` | обёртка над antd `Table`: плотность, липкая шапка, скролл-фейд, пустое состояние, `tabular-nums`, хелперы колонок (деньги/дата/статус/действия); на мобиле — `MobileCardList` через `renderCard` | 61 таблица с собственными настройками |
| `DetailLayout` | страница сущности: шапка (название, статус, ключевые действия) + основная колонка + боковая колонка фактов; на мобиле — один столбец, факты сворачиваются | самодельная двухколонная верстка в DealDetail/ClientDetail/… |
| `FactList` | пары «подпись — значение» с группами и «—» для пустых | `Descriptions` |
| `Section` | стеклянная панель с eyebrow-заголовком и опциональными действиями | `Card title="…"` |
| `StatusPill`, `Money`, `DateText`, `EmptyState`, `Eyebrow` | атомы форматирования и состояния | инлайновые `Tag color=`, `toLocaleString`, `Empty` |

Правило: если один и тот же паттерн нужен на странице третий раз — это примитив, а не копия.
Примитив расширяется пропсом, а не форком в странице.

## 6. Семейства страниц и порядок

Пилот 0 — **Дашборд**: язык дизайна (материал, шрифт, цвет, числа, пустые состояния) по `DASHBOARD.md`.
Пилот 1 — **Клиенты (список) + Карточка клиента**: паттерн таблиц, тулбара и деталей.
Дальше в порядке меню (`PROGRESS.md` — полный список файлов):

1. **Продажи:** сделки (список, создание, карточка, одобрение, история закрытых, архив, аудит,
   override), договоры, доверенности, заметки, отзывы, звонки, дубликаты, маршрут доставки.
2. **Главное:** задачи, сообщения, уведомления, рассылка.
3. **Склад:** товары, группировки, карточка товара, остатки, аудит остатков, движение,
   подтверждение, накладные, зав. склада, согласования, логистика (отгрузки, машина, маршрут).
4. **Финансы:** касса и долги, на проверке, расходы, баланс компании, продажи за день.
5. **ВЭД:** поставщики, импорт-заказы, трекинг и документы, карта, курсы ЦБ.
6. **Аналитика и «Менеджерам»:** самые тяжёлые файлы — разбивать на секции-компоненты,
   графики `@ant-design/charts` с палитрой дашборда (синий акцент, тающая заливка, короткие оси).
7. **AI и РОП-агент:** чат-панели, транскрибация, аудиты.
8. **Система:** команда, сотрудники, карточки сотрудников, посещаемость, HR-журнал, KPI,
   отчёты по звонкам, настройки компании, профиль, телефоны, журнал действий, обновления.

Вне объёма: `LoginPage`, `RatePage`, `ViewportInfoPage`, всё под `/admin/*` (админка сайта без
`.app-shell`).

## 7. Порядок работы в одной сессии

0. Прочитать `BRIEF.md` и `PROGRESS.md`. Взять первое незакрытое семейство (или то, что указал
   пользователь). Вопросов перед стартом не задавать — для спорного есть дефолты в брифе.
1. **Для каждой страницы:** прочитать файл целиком; выписать роли, вопрос страницы, список полей с
   классом P/S/N, действия, текущий мобильный вид. Коротко — в ответе сессии.
2. **Реализовать на примитивах:** убрать инлайновые стили и hex, перевести заголовок / тулбар /
   таблицу / детали, применить правила §4. Логику (запросы, мутации, гейты ролей, URL-параметры,
   формы) не менять. Большой файл — вынести презентационные части в `components/<family>/`,
   поведение не трогать. Страничный `.css` допустим только для раскладки, уникальной для страницы.
3. **Проверка:** `cd frontend && npm run lint && npm run build && npm run test`. Открыть страницу
   в классике — не падает. Если доступен браузер — скриншоты 1440 и 390, светлая и тёмная.
4. **Коммит** на семейство или на 2–4 страницы, как в истории репозитория:
   заголовок `feat(ui): <что> in the new design` или `refactor(ui): …`, тело на английском —
   что изменилось и почему, одним абзацем; в конце `New design only.` если так и есть.
   Не смешивать редизайн с фичами и фиксами логики.
5. **Обновить `PROGRESS.md`** (статус + одна строка решений по данным) и `QUESTIONS.md`
   (если есть). Не больше 5 вопросов за сессию, у каждого — уже применённый дефолт.
6. **Остановиться в чистом состоянии:** сборка зелёная, прогресс записан. Не оставлять семейство
   наполовину — лучше меньше страниц, но до конца по Definition of Done.

## 8. Чего не делать

- Не добавлять в `glass.css` новые правила «на всё приложение» через `.ant-*`, если это решается
  в примитиве. `glass.css` — каркас, дашборд и по-настоящему глобальные вещи.
- Не менять API, Prisma, роли, маршруты, бизнес-тексты, ключи `localStorage`, URL-параметры.
- Не трогать бэкенд, кроме исключения в §4.3.
- Не удалять классику и переключатель до отдельного решения пользователя.
- Не вводить новые зависимости без записи в `QUESTIONS.md`.
- Не делать «редизайн ради редизайна» на рабочих мобильных страницах (§3, п. 11).
- Не писать `!important` в новых стилях (исключение — перекрытие антд-инлайна, с комментарием
  почему).

## 9. Формат `QUESTIONS.md`

```
## 2026-10-20 — Продажи
- [ ] Q1. DealsPage: колонка «Оплата» дублирует статус сделки для закрытых сделок — убрать?
      Дефолт применён: колонка скрыта, способ оплаты виден в дровере сделки.
      Альтернатива: вернуть колонку только для роли ACCOUNTANT.

## BACKLOG (нужны данные с бэкенда)
- ClientsPage: сумма долга клиента в списке (есть в ClientDebtRow, нет в Client списка).
```

Пользователь отвечает галочкой и строкой «Ответ: …»; следующая сессия начинает с разбора ответов.

## 10. Definition of Done для страницы

- Нет инлайновых `style` (кроме динамических значений, зависящих от данных) и нет hex-цветов.
- Заголовок, тулбар, таблица, детали — на примитивах из §5.
- Поля классифицированы; N скрыты, S доступны на клик, добавленные P подписаны.
- Деньги, даты, телефоны, статусы — через хелперы и примитивы §4.4.
- Светлая и тёмная тема, 1440 и 390px; ни одна роль не потеряла действия.
